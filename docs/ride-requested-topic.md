# `ride-requested` Topic

## Purpose

`ride-requested` represents the business fact that RouteX accepted a passenger's request for a ride. It is the entry event for the current asynchronous workflow.

## Event Structure

`RideRequestedEvent` is a Java record in `com.routex.dispatch`:

| Field | Meaning |
| --- | --- |
| `rideId` | UUID generated by RouteX; correlation identifier and Kafka key. |
| `passengerId` | Passenger identifier supplied in the HTTP request. |
| `pickupLocation` | Requested pickup location. |
| `destinationLocation` | Requested destination location. |
| `requestedAt` | `Instant` at which the controller created the event. |

The inbound `RideRequest` is separate from the event. It has `@NotBlank` validation on passenger, pickup, and destination fields; callers do not choose RouteX's ride ID or timestamp.

## Producer

`RideRequestController.requestRide` handles `POST /rides/requests`. It validates the request, creates `RideRequestedEvent`, and calls:

```java
kafkaTemplate.send(KafkaTopicConfiguration.RIDE_REQUESTED_TOPIC, event.rideId(), event);
```

The template type is `KafkaTemplate<String, RideRequestedEvent>`. The endpoint returns `202 Accepted` with the event immediately after this call; it does not wait for the returned asynchronous send result.

## Message Key and Partitioning

The key is `rideId`. `KafkaTopicConfiguration.rideRequestedTopic()` declares three partitions. Kafka maps equal keys consistently to one partition while the partitioning metadata remains unchanged, so events for a ride can retain their partition-local order. The controller does not explicitly specify a partition.

```text
ride-requested
├── partition 0: ride IDs selected by the key partitioner
├── partition 1: ride IDs selected by the key partitioner
└── partition 2: ride IDs selected by the key partitioner
```

Several different ride IDs can map to the same partition. The topic has no global order across these three logs.

## Consumer

`DriverMatchingConsumer.handleRideRequested` is subscribed with:

```java
@KafkaListener(
    topics = KafkaTopicConfiguration.RIDE_REQUESTED_TOPIC,
    groupId = "driver-matching-group"
)
```

It receives a deserialized `RideRequestedEvent` and the received partition header. It delegates to `DriverAssignmentService`, which randomly selects one of three in-memory `Driver` records, then hands the resulting `DriverAssignmentEvent` to `DriverAssignmentProducer`.

## Consumer Group and Concurrency

The effective group is `driver-matching-group`; it overrides the YAML default. The annotation has no `concurrency` attribute and the YAML has no listener concurrency property, so the active listener runs with Spring Kafka's default concurrency of one consumer instance.

With three partitions, this one instance can be assigned all three partitions. If the same group were scaled to three consumer instances, Kafka could assign one partition to each; a fourth or later instance could be idle for this topic.

## Processing Flow

```text
POST /rides/requests
  -> RideRequestController
  -> RideRequestedEvent, keyed by rideId
  -> ride-requested
  -> DriverMatchingConsumer (driver-matching-group)
  -> DriverAssignmentService
  -> DriverAssignmentProducer
  -> driver-assigned
```

## Ordering and Failure Scope

Kafka preserves record order inside an individual partition. Thus the key supports ordering for records of the same ride in this topic, not a total order across rides or topics.

The listener receives an `Acknowledgment` because `spring.kafka.listener.ack-mode` is `manual`. It publishes the assignment, then calls `acknowledgment.acknowledge()` on its successful path. It logs the ride ID, partition, and offset.

For the deliberate `passengerId` value `failure-test`, the listener throws `RuntimeException("Simulated driver matching failure")` **after** publishing the assignment but **before** the acknowledgement. No retry or error handler is configured in application code. A redelivery can therefore publish another assignment for the same source record; manual acknowledgement alone is not idempotency or exactly-once processing. See [delivery scope](consumer-observability-and-delivery-scope.md).
